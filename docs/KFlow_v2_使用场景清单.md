## 一、场景描述格式

每个场景使用统一卡片，**动作与结果均用描述性语言，不依赖具体命令拼写**：

```text
### S<编号> <场景名>
- 角色：Agent / 人类 / 系统 / 两者
- 前置条件：（可选）该场景发生前的项目状态
- 动作：Actor 做了什么（描述性语言）
- KFlow 返回 / 展示：系统给出的结果（描述性语言）
- 边界 / 硬性规则：（可选）该场景必须遵守的约束
- 来源：<文档> §<章节>
```

示例：

```text
### S08 扫描项目检测变化
- 角色：Agent / 人类
- 动作：对已建图的项目发起一次全量检查。
- KFlow 返回 / 展示：比对当前文件内容、推导语义与上次确认基线，给出每个 Node 的变化原因。
- 边界：只读计算，不修改任何文件，不要求人工事先标记"我改过了"。
- 来源：领域模型 §8.1
```

## 二、场景清单

### 类别 A —— 项目初始化与建图（生命周期）

#### S01 初始化 KFlow 项目
- 角色：人类 / Agent
- 前置条件：工作目录是一个 Git 仓库
- 动作：执行项目初始化。
- KFlow 返回 / 展示：在仓库中建立元数据目录（项目清单 + `nodes`/`derivations`/`confirmations` 子目录）；生成让"规范元数据进 Git、缓存与运行时文件不进 Git"的忽略规则；对已初始化的项目再次初始化时给出明确错误提示。
- 边界：初始化不触碰任何用户正文。
- 来源：领域模型 §4.1 §10 **[批准]**

#### S02 注册源知识（绑定文件 + 零输入推导）
- 角色：Agent / 人类
- 前置条件：项目里已存在一个或多个真实文件（如 `docs/requirements.md`、`docs/architecture.svg`）
- 动作：把一个或多个文件登记为知识单元（Knowledge Node），并为它建立一次"零输入"推导作为唯一生产者；同时填写推导的简短/详细说明，以及输出在该推导中的简短/详细含义。
- KFlow 返回 / 展示：确认源 Node 创建成功，返回其稳定身份、显示名和绑定的文件路径。
- 边界：KFlow 不创建空白占位文件；缺失简短/详细说明时拒绝写入；一次零输入推导可同时登记多个共同形成的源 Node；目录、章节、段落、代码片段不能被登记为知识单元。
- 来源：领域模型 §4 §5 §11.1 **[批准]**；`kflow/v2/models.py` **[已实现]**

#### S03 建立普通推导（多输入 → 多输出）
- 角色：Agent / 人类
- 动作：选择若干已有 Node 作为输入，说明每个输入在本次推导中的角色（短/详）；声明一个或多个输出 Node，说明每个输出的生成含义（短/详）；并给整次推导写简短/详细说明。
- KFlow 返回 / 展示：一次创建该推导及全部输出 Node，返回推导与输出 Node 的身份；若输入/输出引用不存在的 Node、输入输出重复、或会形成环，则拒绝并说明原因。
- 边界：一个 Derivation 是不可拆分的整体，不能拆成多条普通二元关系；输入可为零、输出必须至少一个；不允许把固定关系标签（如 derived_from/constrains/implements）作为强制枚举。
- 来源：启动指令 §6；领域模型 §4.3 §5.2 **[批准]**；`kflow/v2/models.py` `graph.py` **[已实现]**

#### S04 修改 Node 元数据（改名 / 增减文件）
- 角色：Agent / 人类
- 动作：重命名一个 Node，或向 Node 增删绑定的文件路径。
- KFlow 返回 / 展示：Node 的稳定身份保持不变；改名不影响其有效版本；文件集合变化会使该 Node 及其全部下游进入"需检查"状态，并指出具体变化的路径。
- 边界：文件路径必须是仓库相对规范路径，同一文件只能属于一个 Node；KFlow 不重命名/移动任何真实文件。
- 来源：领域模型 §5.1 §11.3；审查报告 §5.1 **[批准]**；`kflow/v2/models.py` **[已实现]**

#### S05 修改 Derivation 语义或拓扑
- 角色：Agent / 人类
- 动作：修改一次推导的简短/详细说明，或调整它的输入/输出集合。
- KFlow 返回 / 展示：该推导的全部输出 Node 及其下游都会因"推导变化"而需要重新检查。
- 边界：推导语义或拓扑的任何变化都使 fingerprint 变化，属于保守且可解释的行为；同一推导内不允许重复输入/重复输出或自环。
- 来源：领域模型 §6.3 §11.3；启动指令 §9.3 **[批准]**；`kflow/v2/versioning.py` **[已实现]**

#### S06 变更 Node 的生产者（rewire）
- 角色：Agent / 人类
- 动作：把某个现有 Node 的"唯一生产者"从一个推导改挂到另一个推导。
- KFlow 返回 / 展示：在单个事务内完成"移除旧生产者关系 + 建立新生产者关系"，过程中绝不暴露非法中间图；若会导致违反"每个 Node 恰好一个生产者"或产生环，则拒绝。
- 来源：领域模型 §11.2 **[批准]**

#### S07 删除元数据（Node / Derivation / Confirmation）
- 角色：Agent / 人类
- 动作：移除某个 Node 及其关联元数据，或从多输出推导中移除一个输出。
- KFlow 返回 / 展示：默认只删除 KFlow 元数据，被管理的真实文件保持原样；有下游消费的 Node 默认拒绝删除，必须先显式重新挂接或明确级联移除范围；删除最后一个输出时连带删除该推导；删除 Node 时删除其确认记录。
- 边界：KFlow 不是编辑器，任何情况下不得创建、编辑、移动或删除用户正文。
- 来源：领域模型 §11.4 §14；启动指令 §4.2 **[批准]**

### 类别 A 修改建议（评审用 · 2026-08-21）

> 状态：**建议稿**，未覆盖上述原场景。原 S01–S07 保持原样，本板块为产品负责人对 Category A 的修改意见，最终检查通过后合并回正式场景。

#### 决策记录

| 编号 | 决策 | 内容 | 状态 |
|---|---|---|---|
| D-A1 | 采用"无生产者"源节点模型 | 新建 Node 即孤立节点；**derivation 必须 ≥1 输入**，零输入 derivation 特性整体取消；入度 0 的 Node 自动视为源。推翻已批准 D1 / Q1。 | **已确认** |
| D-A2 | 源节点不保存"为什么存在"说明 | KFlow 对源节点零语义，靠文件名与内容自身表达。 | **已确认** |
| D-A3 | detail 全允许为空、short 必须非空 | 适用于 derivation / input / output 全部三层。 | 建议 |
| D-A4 | rewire 不作为独立操作 | 并入"修改 derivation"：先移除旧输出、再在另一 derivation 添加输出。 | 建议 |
| D-A5 | 生命周期收敛为 7 个操作 | 新建 KFlow/Node/derivation、修改 Node/derivation、删除 Node/derivation。 | 建议 |
| D-A6 | Node 严格、Derivation 宽松 | 删除 Node 仅当不属于任何 derivation 的输入或输出；修改/删除 derivation 任何情况允许（仍需过图不变量：≥1 输入、至多 1 生产者、无环）。 | 建议 |
| D-A7 | 删除 derivation 的护栏 | 同步删除其输出 Node 的 Confirmation，并在结果中报告哪些 Node 因此变成孤立/源节点。 | 建议 |

#### 决策依据（项目经理评估）

1. **实体 / 关系分离更自然**：Node 是独立实体、Derivation 是连接关系；"先建孤立节点、再接线"符合真实工作流。7 个操作边界均清晰。
2. **改动互相咬合自洽**：D-A4（rewire 并入修改）成立的前提正是 D-A1——孤立中间态始终合法，rewire 无需特殊事务，崩溃也只停在合法状态。
3. **迁移显著简化**：v1 源 Node 本无 producing derivation，可原样迁移，取消"为源 Node 补建零输入 derivation"的人工阻塞项；配合 D-A3，"缺 detail 必须补全"阻塞项亦消失。
4. **必须接受的代价**（已确认接受）：
   - 推翻已批准 D1/Q1 及启动指令"必须支持零输入 derivation"的硬要求，需回改三份文档与 `kflow/v2` 代码；
   - 源节点在 KFlow 中零语义；原零输入多输出 derivation 的"共同登记分组"能力一并取消；
   - 新 Node 一律孤立，图谱完备性依赖使用者主动接线（validate 不再对孤立节点告警）。
5. **需加护栏的漏洞**：宽松的"删除 derivation"会把派生节点静默降级为源节点，绕过 Node 删除的严格性，因此必须有 D-A7（清 Confirmation + 报告受影响 Node）。

#### 修改后的 Category A 场景卡片（建议稿）

##### S01 新建 KFlow（初始化项目）
- 角色：人类 / Agent
- 动作：在 Git 仓库中执行初始化。
- KFlow 返回 / 展示：建立元数据目录（项目清单 + `nodes`/`derivations`/`confirmations` 子目录）；生成"规范元数据进 Git、缓存与运行时文件不进 Git"的忽略规则；对已初始化项目再次初始化时明确报错。
- 边界：不触碰用户正文。
- 来源：原 S01，**无改动**。

##### S02 新建 Node
- 角色：Agent / 人类
- 动作：把一个或多个已存在文件登记为一个知识单元，填写项目内唯一名称。
- KFlow 返回 / 展示：创建一个初始**孤立**的 Node（不属于任何 derivation），返回其稳定身份、显示名和绑定文件路径；源身份由后续图结构自动决定（入度 0 即源）。
- 边界：KFlow 不创建占位文件；文件路径为规范仓库相对路径、同一文件唯一归属、注册时文件必须存在；不保存任何"为什么存在"的说明；**不需要同时创建 derivation**。
- 来源：取代原 S02"注册源知识"。

##### S03 新建 derivation
- 角色：Agent / 人类
- 动作：选择 **≥1 个**输入 Node，声明 1..n 个输出 Node；填写 derivation `short`、每个 input `short`、每个 output `short`（所有 `detail` 均可为空）。
- KFlow 返回 / 展示：一次创建该 derivation 及全部输出 Node，返回其身份；输出 Node 当前必须无生产者；整个 Node 图必须保持无环；违规时拒绝并说明原因。
- 边界：**零输入 derivation 不再允许**；一个 derivation 是不可拆分的整体（不能拆成多条普通二元关系）；不允许固定关系标签枚举；同一 derivation 内输入/输出不得重复或自环。
- 来源：修改自原 S03。

##### S04 修改 Node
- 角色：Agent / 人类
- 动作：重命名一个 Node，或增删绑定的文件路径。
- KFlow 返回 / 展示：Node 稳定身份不变；改名不影响有效版本；文件集合变化使该 Node 及全部下游进入"需检查"状态，并指明具体变化的路径。
- 边界：路径规范、同一文件唯一归属；KFlow 不重命名/移动真实文件。
- 来源：原 S04，**无改动**。

##### S05 修改 derivation
- 角色：Agent / 人类
- 动作：修改 derivation 的 `short/detail`，或增删它的输入/输出节点。
- KFlow 返回 / 展示：文本与拓扑改动均允许（任何情况）；拓扑改动必须保持图不变量（**≥1 输入、输出 Node 至多一个生产者、无环**）；被增删的输出 Node 及其下游进入"需检查"状态、其 Confirmation 失效；此操作同时覆盖"变更 Node 的生产者"。
- 边界：变更生产者不需要独立操作，也不需要特殊事务——孤立中间态始终合法。
- 来源：合并原 S05 与 S06。

##### S06 删除 Node
- 角色：Agent / 人类
- 动作：删除一个 Node 及其确认记录。
- KFlow 返回 / 展示：**仅当该 Node 不属于任何 derivation 的输入或输出时允许**；被拒绝时列出关联的 derivation 与下游，引导先解绑；被管理的真实文件保持原样。
- 边界：绝不创建/编辑/移动/删除用户正文；Node 删除是 7 个操作中最严格的。
- 来源：拆分自原 S07 的 Node 部分。

##### S07 删除 derivation
- 角色：Agent / 人类
- 动作：删除一条 derivation。
- KFlow 返回 / 展示：**任何情况允许**；删除后其输出 Node 变为孤立（自动成为"源"）；**同步删除这些输出 Node 的 Confirmation**（变为未确认）；**明确报告哪些 Node 因此变成孤立/源节点**。
- 边界：不删除任何 Node 本体与用户文件；删除 derivation 只解除连接，不视为删除"推导出的知识"。
- 来源：拆分自原 S07 的 Derivation 部分。

#### 跨板块影响与回改清单（先行备注，不在本板块落实）

**Category B（状态与检测）**
- 状态 reason 仅对**有生产者**的 Node 可能为 `derivation_changed`；源 Node 永不 `derivation_changed`，也永不 `input_changed`，只可能是 `unconfirmed` / `files_changed`。
- Confirmation schema 需支持"无 producing_derivation / 无输入向量"的变体。
- 有效版本：源分支 = `hash([node.id, files_fingerprint])`，不含 derivation 与输入分量。

**Category C（影响与 Agent 查询）**
- 源 Node 的 `upstream` 退化为仅自身；`neighborhood` / `sibling_outputs` 无生产者时为空，只展示它作为输入参与的 derivation。
- `changed_nodes` / `affected_nodes` / `review_order` / `roots` 语义不变；`files_changed` 的源 Node 仍可作为变化根。

**Category D（确认闭环）**
- 对源 Node 执行确认时，基线不含 producing_derivation 分量；对派生 Node 确认逻辑不变。

**Category G（存储、恢复、维护）**
- validate：**删除"孤立节点"告警**（孤立现在是合法状态）；生产者不变量由"恰好一个"改为"**至多一个**"（`missing_producer` 不再视为错误）。

**Category H（v1 迁移）**
- v1 源 Node（无 producing derivation）直接迁移为孤立 Node，取消"补建零输入 derivation"人工阻塞项。
- v1 derivation 本都 ≥1 输入，满足新不变量；缺 detail 因 D-A3 不再阻塞。
- 仍不迁移：红黄绿状态、级联确认结果、`index.json`。

- `models.py`：Derivation 需强制 ≥1 输入（当前允许空输入）。

- `versioning.py`：`compute_effective_versions` 现对每个 Node 取 producer，需增加源分支。
- `tests/v2/`：按新不变量更新。

**已批准文档回改清单（最终合并时）**
- `KFlow_v2_重构启动指令.md`：§6.1 删除"必须支持零输入 derivation"；§6.5 源 Node 表达；§9 确认语义涉及 producer 的部分。

### 类别 B —— 变化检测与状态

#### S08 扫描项目检测变化（scan）
- 角色：Agent / 人类 / 系统
- 动作：对已建图项目发起一次全量只读检查。
- KFlow 返回 / 展示：加载并校验元数据，读取 Node 文件计算指纹，按拓扑序计算推导指纹与有效版本，与确认基线对比，给出每个 Node 的"变化原因"（无确认 / 自身文件变化 / 推导变化 / 直接输入变化）。
- 边界：不再依赖人工执行"我改过了"；首版不需要文件监听、钩子或常驻服务；可选更新本地可重建缓存，但不改变共享状态。
- 来源：领域模型 §8.1 **[批准]**

#### S09 查看某个 Node 的状态及原因（status）
- 角色：Agent / 人类
- 动作：查询一个或多个 Node 的当前状态。
- KFlow 返回 / 展示：对每个 Node 返回可并存的 reason 列表：
  - `unconfirmed`（从未确认）
  - `files_changed`（自身文件/路径变化）
  - `derivation_changed`（生产推导变化）
  - `input_changed`（直接输入有效版本不同）
  - 并派生 `needs_review`（有原因）与 `current`（无原因）。
- 边界：状态是派生结果，不是持久化颜色字段；校验问题（文件缺失/图非法）与审查状态分开返回，不伪装成"红色状态"。
- 来源：领域模型 §7.1 **[批准]**

#### S10 多文件 Node 中任一文件变化
- 角色：Agent / 系统
- 动作：一个 Node 绑定了多个文件，其中任一文件内容或路径发生变化后再次扫描。
- KFlow 返回 / 展示：该 Node 被识别为 `files_changed`，并明确指出变化的那个具体文件路径，而不是笼统标红整个 Node。
- 来源：领域模型 §14 验收矩阵；审查报告 §5.2 **[批准]**

#### S11 文件重命名 / 路径变化
- 角色：Agent / 人类
- 动作：重命名一个受管文件，并同步更新 Node 的文件路径。
- KFlow 返回 / 展示：Node 的稳定身份不变；路径变化被识别为 Node 变化，目标 Node 及下游需要重新检查。
- 来源：领域模型 §6.2 §14；审查报告 §5.2 **[批准]**

#### S12 内容恢复为旧版本
- 角色：Agent / 人类
- 动作：某个 Node 的文件内容被改后又精确恢复为与上次确认一致的版本，再次扫描。
- KFlow 返回 / 展示：有效版本随之恢复，KFlow 按当前事实判断状态，不再保留"发生过临时变化"的痕迹。
- 边界：符合"不引入事件溯源"的边界——系统不永久记录每次扫描。
- 来源：领域模型 §6.4 §8.2 **[批准]**

#### S13 文件缺失 / 未登记文件
- 角色：Agent / 系统
- 动作：受管 Node 指向的文件从磁盘消失，或 `docs/` 下出现未登记的新文件。
- KFlow 返回 / 展示：以 validation / scan issue 形式报告，而不是伪装成颜色状态；列出具体缺失或未登记的路径。
- 来源：领域模型 §5.1 §7.1；审查报告 §8 **[批准]**

### 类别 C —— 影响分析与 Agent 查询（Agent 接口）

#### S14 修改后查询影响（impact）
- 角色：Agent
- 动作：人类或 Agent 修改了若干文件后，Agent 调用一次影响查询。
- KFlow 返回 / 展示：基础结果优先包含——
  - 已变化的 Node 及其全部文件路径、具体变化路径；
  - 受影响 Node（含文件路径、直接/传递层级 depth、经过的 Derivation、来自哪些变化根）；
  - 稳定的拓扑检查顺序 review_order；
  - 状态原因列表；
  - 阻断性校验问题。
- 边界：只返回"可能受影响"，不声明"必须修改"；绝不含正文。
- 来源：启动指令 §8.1；领域模型 §9.1 **[批准]**

#### S15 修改前查询前提（upstream / context）
- 角色：Agent
- 动作：Agent 在修改某个 Node 之前，先查询它的上游前提。
- KFlow 返回 / 展示：该 Node 的全部前提 Node、对应文件路径以及经过的 Derivation，按拓扑序排列。
- 边界：KFlow 只告诉"应该关注哪些文件以及为什么"，不打开、不传递这些文件。
- 来源：启动指令 §8.2；领域模型 §9.3 **[批准]**

#### S16 查询邻域（neighborhood）
- 角色：Agent
- 动作：Agent 围绕某个 Node 查询它"所在的推导上下文"。
- KFlow 返回 / 展示：该 Node 的生产推导的输入、输出及其语义，并显式展示同源的其他输出（sibling outputs），提醒判断该次推导是否也需要更新。
- 来源：领域模型 §7.3 §9.3 **[批准]**；`kflow/v2/graph.py` `sibling_outputs` **[已实现]**

#### S17 从指定 Node 显式追踪影响（affect）
- 角色：Agent / 人类
- 动作：无论某个 Node 当前是否已确认，都从它出发向下游做拓扑遍历。
- KFlow 返回 / 展示：以该 Node 为根的全部下游，含层级深度与经过路径；不依赖该 Node 当前是否为"变化根"。
- 来源：领域模型 §8.2 **[批准]**

#### S18 多变化根合并
- 角色：Agent
- 动作：多个 Node 同时变化，Agent 查询整体影响。
- KFlow 返回 / 展示：多个受影响目标合并呈现，每个目标保留最小深度、全部直接来源根与可解释路径；review order 是所有需检查 Node 构成子图的稳定拓扑序，同层按稳定规则排序。
- 来源：领域模型 §8.2 §9.1 **[批准]**

#### S19 可选展开 Derivation 语义与确认差异
- 角色：Agent
- 动作：Agent 在基础影响结果之上，按需请求更详细的信息。
- KFlow 返回 / 展示：可返回涉及的 Derivation ID、推导 short/detail、输入/输出 short/detail、影响路径、生产推导的同源输出、确认记录中的 fingerprint/版本差异。
- 边界：任何展开模式都禁止返回正文、片段、摘要或拼装 Prompt。
- 来源：领域模型 §9.2 **[批准]**

#### S20 组合查询 / 不强制单一工作流
- 角色：Agent
- 动作：Agent 可自由选择查询方式——修改前一次性查询上游和下游形成整体计划，或修改一个文件后逐层查询影响，或混合使用。
- KFlow 返回 / 展示：提供相互独立、可组合的查询方向（upstream / downstream / neighborhood / status-impact），不强迫 Agent 使用唯一策略，也不自动打开任何文件。
- 来源：启动指令 §8.2；领域模型 §9.3 **[批准]**

### 类别 D —— 确认闭环（confirm）

#### S21 逐 Node 确认（confirm）
- 角色：Agent / 人类
- 动作：对某个已检查的 Node 执行确认，声明"已检查该 Node 的当前文件、生产推导和当前直接输入条件，认为它仍成立或已完成必要修改"。
- KFlow 返回 / 展示：记录目标 Node 的三部分基线——自身文件集合指纹、生产推导指纹、直接输入有效版本向量；返回目标状态、此前的变化原因，以及仍待检查的下游摘要。
- 边界：目标 Node 必须存在且图可读，存在阻断性校验错误时拒绝；确认只写目标 Node 的确认文件；不要求人工再次批准，Agent 可独立确认；不存在任何级联确认。
- 来源：启动指令 §9；领域模型 §7.2 §5.3 **[批准]**

#### S22 确认不级联（两个经典验证）
- 角色：Agent / 人类
- 动作：在 `A,B → C,D` 中确认 C，或在 `A → B → C` 中确认 B。
- KFlow 返回 / 展示：确认 C 绝不修改 D；确认 B 后 C 仍保持"待检查"——因为 C 的旧确认仍记录旧的 B 有效版本。
- 边界：同一推导的多个输出必须分别确认；下游状态通过有效版本逐层推导，确认上游不会清除下游确认记录。
- 来源：领域模型 §7.2 §7.3 §14；审查报告 §9 **[批准]**

#### S23 修改 Node 时检查生产推导
- 角色：Agent
- 动作：Agent 修改了某个 Node 的内容后，检查它的生产推导是否仍然准确。
- KFlow 返回 / 展示：辅助 Agent 核对 inputs 是否仍正确、input short/detail 是否准确、推导及 output 的 short/detail 是否描述当前状态、是否需要增删输入、同源输出是否受影响。
- 边界：若内容变化没有改变推导逻辑，不应机械修改推导元数据；若方向/依据/形成方式变化，则必须同步更新元数据。
- 来源：启动指令 §9.3 **[批准]**

#### S24 同源输出提醒
- 角色：Agent
- 动作：查询多输出推导中的某一个输出 Node。
- KFlow 返回 / 展示：展示其生产推导和同源的其他输出（sibling），提醒 Agent 判断该次推导是否也需更新；C 自身文件变化不会自动宣称 D 受影响。
- 来源：领域模型 §7.3 **[批准]**；`kflow/v2/graph.py` **[已实现]**

### 类别 E —— 人类界面（Human Interface）

#### S26 项目总览
- 角色：人类
- 动作：打开项目总览页。
- 展示：关键知识对象、最近变化、待复查对象、尚未确认对象、缺失来源、高影响节点。
- 来源：重构计划书 §阶段5-核心页面（草案）**[草案]**；领域模型 §13 阶段7 **[规划]**

#### S27 图谱视图与导航
- 角色：人类
- 动作：在图谱视图中浏览、过滤、聚焦。

- 边界：人类看到的状态必须与 Agent/核心引擎一致（同一事实源，不维护两套关系）。

#### S28 节点详情
- 角色：人类
- 动作：点击某个节点。
- 展示：文件位置、上游来源、下游影响、由哪个推导产生、当前状态与原因、最近复查与确认情况。

#### S29 变化时间线 / 历史比较
- 角色：人类
- 动作：查看一段时间内的项目结构变化，或对比两个 Git 版本。
- 展示：哪些 Node/Derivation 被新增、删除或修改；一次大幅重写前后的知识结构差异；某个 Node 过去对应什么方案。
- 边界：首期只保证元数据可被 Git 正确比较（checkout 任意 commit 可由该版本规范文件重建图和确认基线）；当前阶段不实现历史 UI、快照、重放或事件溯源。
- 来源：启动指令 §10；领域模型 §10.3 §13 **[规划]**

#### S30 从图谱跳转文件
- 角色：人类
- 动作：在图谱中点击某节点对应的文件路径。
- 展示：在编辑器中打开对应文档；直接理解"这份文档为什么存在、由什么产生、影响哪些下游"。
- 来源：启动指令 §3.2 **[批准/规划]**

#### S31 风险与待复查视图
- 角色：人类
- 动作：查看当前有哪些节点需要复查。
- 展示：需检查 Node 列表、变化原因、建议的拓扑检查顺序；在 AI 快速推进项目时保持对结构演化的掌握。
- 来源：启动指令 §3.2 §8.1 **[批准/规划]**

### 类别 F —— Agent 接口规范与硬边界

#### S32 任何 Agent 输出禁止含正文
- 角色：Agent / 系统
- 动作：Agent 请求影响、上下文、状态或任何查询。
- KFlow 返回 / 展示：只返回拓扑、状态原因、文件路径和 Derivation 语义；绝不返回文档全文、片段、自动抽取的上下文文本、拼装后的 Prompt 或临时摘要。
- 边界：KFlow 可以为内部变化检测读取文件、算 hash、读 Git 信息，但不得把正文作为上下文输出给 Agent（硬约束）。
- 来源：启动指令 §4.1；领域模型 §3 **[批准]**

#### S33 JSON 机器契约
- 角色：Agent / 系统
- 动作：Agent 以机器可读方式请求查询结果。
- KFlow 返回 / 展示：返回结构稳定的 JSON 契约，包含 `changed_nodes`、`affected_nodes`、`review_order`、`issues` 等字段；错误与成功分离，错误走标准错误流并带明确错误类型与非零退出码。
- 来源：领域模型 §9.1；v1 设计文档 §6.14 §7（工程框架沿用）**[批准]**

#### S34 校验问题与审查状态分离
- 角色：Agent / 系统
- 动作：项目存在文件缺失或图非法问题时，Agent 查询状态。
- KFlow 返回 / 展示：校验问题（validation issue）作为独立的 `issues` 返回，不混入"需检查/当前"审查状态，不伪装成颜色；只报告，不静默修复。
- 来源：领域模型 §7.1 §9.1 **[批准]**

### 类别 G —— 存储、恢复与维护

#### S35 缓存重建（reindex）
- 角色：人类 / Agent / 系统
- 动作：删除本地索引或缓存后，请求重建。
- KFlow 返回 / 展示：从 `nodes/`/`derivations/`/`confirmations/` 规范分文件完整重建全部派生数据（索引、邻接、状态、review order）。
- 边界：索引、缓存、锁是可重建的派生数据，不是真相源；缓存删除不影响任何确认基线。
- 来源：领域模型 §10.1 §11.3 §14 **[批准]**

#### S36 完整性校验（validate）
- 角色：人类 / Agent
- 动作：对项目做一次完整性检查。
- KFlow 返回 / 展示：逐项报告校验问题——重复 Node ID/名称、文件被多 Node 归属、悬挂引用、缺失生产者、多生产者、环、文件缺失、schema 损坏等；只报告，不自动猜测修复。
- 边界：读操作与写操作前后都会校验；Git 合并产生非法图时同样报出。
- 来源：领域模型 §5 §8.2 §15 **[批准]**；`kflow/v2/graph.py` **[已实现]**

#### S37 崩溃恢复与原子写入
- 角色：系统
- 动作：写入过程中进程中断或磁盘异常。
- KFlow 返回 / 展示：单文件更新使用临时文件 + 原子替换；涉及多规范文件的操作通过临时事务清单可回滚或继续；故障后不留下不可恢复的半图。
- 边界：临时事务只用于崩溃恢复，不进 Git，不构成事件历史；同一工作区首版单写者，不承诺并发写合并。
- 来源：领域模型 §10.2 §15 **[批准]**

#### S38 checkout 历史 commit 后重建
- 角色：人类 / Agent
- 动作：切到仓库的某个历史 commit。
- KFlow 返回 / 展示：仅凭该版本中的规范元数据（Node/Derivation/Confirmation）即可重建该版本的拓扑和确认基线。
- 来源：领域模型 §10.3 §14 **[批准]**

### 类别 H —— v1 一次性迁移

#### S39 只读预检（preflight）
- 角色：人类
- 动作：对既有 v1 项目执行迁移前预检。
- KFlow 返回 / 展示：只读分析并列出阻塞项与预期变更——`file=null` 的 Node、缺少独立 detail 的推导、缺少零输入推导的源 Node、双向引用不一致、重复生产者、路径冲突、缺失文件等；预检不写任何文件。
- 边界：迁移前先复制/备份，绝不原地覆盖 v1 元数据。
- 来源：领域模型 §12.3 §12.5 **[批准]**

#### S40 人工补全映射
- 角色：人类
- 动作：针对预检发现的语义缺失（如推导缺少 detail、源 Node 缺少零输入推导）逐项补全。
- KFlow 返回 / 展示：提供补全映射模板；缺失的语义必须人工填写，迁移器绝不虚构；只有全部阻塞项解决且 v2 校验通过后，才允许显式切换。
- 来源：领域模型 §12.1 §12.3 §12.5 **[批准]**

#### S41 一次性转换 + 对账 + 回滚
- 角色：人类
- 动作：执行迁移，把 v1 元数据转换为独立 v2 数据。
- KFlow 返回 / 展示：可机械映射的部分自动转换（保留 ID、`file→files`、`summary→short`、`role→input.short`、`method→output.short` 等）；输出到显式目标并生成 Node/Derivation/文件归属计数对账；给出回滚/备份说明；v2 运行时不同时读取或写回 v1 schema。
- 边界：正文零写入；不迁移红黄绿状态、级联确认结果和 `index.json`；转换结果需人工审查后才替换使用。
- 来源：领域模型 §12；审查报告 §8 §12 **[批准]**

#### S42 迁移后的初始状态与重扫重确认
- 角色：Agent / 人类
- 动作：迁移完成后首次使用 v2。
- KFlow 返回 / 展示：迁移后的 Node 初始均为 `unconfirmed`，需要执行一次扫描并逐个 Node 确认后才形成审查基线。
- 来源：领域模型 §12.4 **[批准]**

## 三、两类接口的完整闭环

把以上场景串成两条主线：

**Agent 主线（已批准，优先）**
