# KFlow v2 重构计划书

> 面向人类与 AI Agent 协同开发的结构化项目记忆、上下文路由与变更追踪系统  
> 版本：Draft 1.0  
> 适用对象：项目负责人自用  
> 当前策略：先重定义产品，再重构系统；优先验证 Agent 侧价值，随后建设人类侧知识图谱

---

## 1. 执行摘要

KFlow 当前版本已经证明了一个基本概念：可以用 DAG 描述知识节点、推导关系和变更影响。但它还没有真正解决最核心的问题：

1. **Agent 不知道当前任务究竟需要哪些文档，也不知道一处变化会影响哪些知识。**
2. **人类难以从快速增长的文档和 AI 生成内容中持续掌握项目结构、演化过程和风险。**

因此，下一阶段不应继续在现有 CLI 上堆叠功能，而应进行一次以产品定义和领域模型为中心的 v2 重构。

KFlow v2 的北极星目标是：

> **让 Agent 少读无关内容，让人类始终看得懂项目。**

KFlow v2 将由一个共享的知识与变更模型支撑两个界面：

- **Agent Interface**：提供最小充分上下文、影响范围、复查顺序和结构化查询。
- **Human Interface**：提供知识拓扑、文档导航、状态风险和项目认知历史。

本计划建议采用“阶段验证、逐层扩张”的方式推进。短期不追求完整产品，而优先完成以下闭环：

```text
文档发生变化
→ KFlow 识别变化
→ KFlow 计算影响子图
→ Agent 获取最小上下文
→ Agent 更新受影响文档
→ KFlow 记录复查与确认结果
→ 人类可以看到发生了什么
```

## 2. 项目重新定位

### 2.1 产品定义

KFlow 是：

> **面向人类与 AI Agent 协同开发的 Git-native 项目记忆、上下文路由和变更智能层。**

它不替代文档系统、Git、代码编辑器或 AI Agent，而是位于这些系统之上，维护以下事实：

- 项目中有哪些重要知识对象；
- 知识对象之间存在什么语义关系；
- 某次变化可能影响哪些对象；
- 哪些对象已经复查，哪些仍然存在风险；
- 项目的知识结构如何随时间演化；
- 当前任务应向 Agent 提供哪些上下文，以及提供到什么程度。

### 2.2 面向 Agent 的价值

KFlow 应帮助 Agent：

- 避免每次修改后扫描整个文档群；
- 区分直接依赖、传递影响和一般关联；
- 按优先级获取上下文；
- 只读取必要文档或必要片段；
- 获得明确的复查顺序；
- 在任务完成后回写变更、确认和证据。

### 2.3 面向人类的价值

KFlow 应帮助工程师：

- 快速理解项目文档和设计知识的整体结构；
- 从图谱直接跳转到目标文档或具体章节；
- 看见最近发生的结构变化；
- 识别尚未复查、来源缺失或存在矛盾风险的节点；
- 理解某项设计是如何形成的；
- 追踪 AI 做了什么、为什么做、影响了什么；
- 在 AI 高速推进项目时保持认知和决策控制。

## 3. 核心设计理念

后续每个功能都必须接受以下原则检验。

### 3.1 KFlow 管理结构、关系和变化，不接管知识内容

知识内容继续存在于：

- Markdown 文档；
- 代码文件；
- 配置文件；
- 数据、实验和报告；
- 外部文档引用。

KFlow 只保存其元数据、关系、状态和历史。

### 3.2 上下文必须“最小且充分”

KFlow 不追求给 Agent 更多内容，而追求：

```text
当前任务
→ 找到相关子图
→ 按距离和重要性分层
→ 输出最小充分上下文
```

建议后续支持上下文级别：

- **L0：目标对象**——必须读取完整内容；
- **L1：直接上下游**——通常读取全文或相关章节；
- **L2：传递依赖**——读取摘要、关系和关键片段；
- **L3：外围关联**——只提供名称、状态和跳转地址。

### 3.3 关系必须具备明确语义

不能只保存 `A → B`，还应说明：

- A 为什么与 B 有关；
- A 在 B 中发挥什么作用；
- A 的改变是否必然使 B 失效；
- 该关系由人、Agent 还是自动规则建立；
- 关系是否经过人工确认。

初期可优先支持：

- `derived_from`：由其推导；
- `constrained_by`：受其约束；
- `implements`：实现某项设计；
- `validated_by`：被实验或测试验证；
- `supersedes`：替代旧方案；
- `contradicts`：存在冲突；
- `references`：一般引用。

### 3.4 历史记录的是“项目认知结构的演化”

Git 记录文件行级变化，KFlow 不应重复 Git。

KFlow 应记录：

- 节点何时产生；
- 关系何时建立、改变或删除；
- 某次文档变化触发了哪些影响；
- 哪些节点被重新复查；
- 谁确认了某项结论；
- 哪个方案替代了哪个方案；
- 某个时间点的项目知识拓扑是什么样。

### 3.5 KFlow 缩小范围，但不冒充真理判断器

KFlow 可以判断：

- 上游发生了变化；
- 某些下游可能受到影响；
- 哪些内容需要复查；
- 哪些来源已经缺失。

KFlow 不应直接声称：

- 某个结论一定错误；
- 某份文档已经自动完全一致；
- Agent 的修改一定正确。

最终语义判断由 Agent 或人完成，KFlow 负责提供证据、边界和流程。

### 3.6 Agent 和人类必须共享同一事实源

Agent 查询的影响子图与人类看到的图谱必须来自同一核心模型。

禁止形成两套逻辑：

```text
Agent 使用一套依赖模型
人类界面使用另一套图谱模型
```

## 4. 当前项目诊断

### 4.1 可以保留的资产

当前 KFlow v0.1 中值得保留的资产包括：

- Node / Derivation 的基本抽象；
- 上下游遍历、拓扑排序和环检测经验；
- `context` 与 `affect` 两类查询方向；
- CLI 与 JSON 输出的基本工程框架；
- 文档内容与关系元数据分离的思想；
- 已有测试和命令行为，可作为回归参考；
- 项目名称、定位基础和 README 中的使用场景。

### 4.2 不应直接继承的假设

以下设计不应被当作 v2 的既定前提：

- 一个 Node 必须对应整份 Markdown 文件；
- 所有关系都必须通过“多输入单输出 Derivation”表达；
- `green / yellow / red` 可以承载全部状态；
- 用户会主动执行 `modify` 通知系统；
- `.kflow/` 元数据不需要进入 Git；
- CLI 是主要交互入口；
- 图谱只需要展示当前静态状态；
- 一次 `confirm --cascade` 可以安全恢复全部下游；
- 只要支持 JSON 就已经足够面向 Agent。

### 4.3 建议的重构方式

不建议直接在 `main` 上渐进式修改现有实现。

建议：

1. 为当前版本打标签，例如 `v0.1.0-legacy`；
2. 保留当前版本作为概念验证和行为参考；
3. 新建 `v2` 或 `next` 开发分支；
4. 先完成产品与架构文档，再开始核心代码；
5. 旧代码仅按模块选择性迁移，不做机械式重写；
6. v2 达到最小闭环后，再决定是否完全替换 v0.1。

## 5. 项目范围与非目标

### 5.1 v2 第一阶段必须解决

- 项目知识对象建模；
- 语义关系建模；
- 文件或章节变化检测；
- 影响子图计算；
- Agent 可消费的上下文包；
- 复查与确认流程；
- 基础历史事件；
- 最小可用的人类图谱视图；
- Git 友好的持久化；
- 可测试、可恢复、可迁移。

### 5.2 第一阶段暂不解决

- 完整的多人权限系统；
- 云端协作平台；
- 大规模企业知识图谱；
- 通用向量数据库；
- 自动替代人工确认；
- 复杂的实时协同编辑；
- 所有 IDE 和 Agent 的全面集成；
- 高度定制化的图谱美术效果；
- 商业化、计费、账号和组织管理；
- 面向百万节点的大规模性能优化。

## 6. 建议的核心领域模型

这一部分不是最终架构，而是重构期间必须优先澄清的对象边界。

### 6.1 KnowledgeObject

表示项目中的重要知识对象。

可能对应：

- 整份文档；
- 文档中的标题或章节；
- 需求；
- 设计决策；
- 假设；
- 接口规范；
- 实验；
- 结论；
- 代码模块；
- 外部来源。

建议字段：

```text
id
type
title
locator
summary
content_fingerprint
created_at
updated_at
created_by
metadata
```

`locator` 应支持：

```text
docs/architecture.md
docs/architecture.md#runtime-model
src/scheduler.py::Scheduler
external://paper/xxx
```

### 6.2 Relation

表示两个知识对象之间的语义联系。

建议字段：

```text
id
source
target
type
role
strength
impact_policy
evidence
created_by
confirmed_by
created_at
valid_from
valid_to
```

其中 `impact_policy` 用于描述：

- 上游变化后，下游必须复查；
- 仅当特定章节变化时复查；
- 只是弱关联，不自动传播；
- 来源删除后，下游失去依据。

### 6.3 ChangeEvent

记录一次知识对象或关系变化。

示例：

```text
ObjectCreated
ContentChanged
RelationAdded
RelationRemoved
RelationChanged
ReviewRequested
ReviewCompleted
ObjectConfirmed
ObjectInvalidated
ObjectSuperseded
SnapshotCreated
```

### 6.4 ReviewRecord

记录一次复查，不与对象当前状态混为一谈。

建议字段：

```text
object_id
trigger_event
reviewer
reviewer_type
decision
evidence
reviewed_at
content_fingerprint
```

### 6.5 ContextBundle

KFlow 面向 Agent 的核心输出对象。

建议包含：

```text
task
target_objects
required_context
supporting_context
affected_objects
excluded_objects
review_order
relation_explanations
token_budget
content_resolution
```

### 6.6 Snapshot

用于表示某个时间点的知识拓扑状态。

初期可以只保存：

- 事件偏移量；
- Git commit SHA；
- 关键对象和关系摘要。

无需立即保存完整图副本。

## 7. 总体工作分解

项目建议拆成七条并行但有先后依赖的工作流。

### 工作流 A：产品定义

目标：

- 把宽泛理念转化为明确用户场景；
- 确立 MVP 边界；
- 定义核心成功指标；
- 排除伪需求和过度设计。

主要产物：

- 产品愿景；
- 用户角色；
- 核心场景；
- 用户故事；
- 非目标；
- MVP 定义；
- 术语表。

### 工作流 B：领域模型与架构

目标：

- 重构核心对象；
- 明确状态、事件、历史、关系和上下文的边界；
- 决定存储、索引和 Git 策略；
- 设计扩展接口。

主要产物：

- 领域模型；
- 关系类型系统；
- 状态计算规则；
- 事件模型；
- 存储格式；
- API 契约；
- 架构决策记录。

### 工作流 C：Agent 上下文引擎

目标：

- 根据任务和变化生成最小充分上下文；
- 输出影响范围、优先级和复查顺序；
- 支持 Codex / Claude Code 调用。

主要产物：

- `impact` 查询；
- `context bundle`；
- token 预算策略；
- JSON / MCP 接口；
- Agent 使用指南；
- 基准测试。

### 工作流 D：知识图谱与人类界面

目标：

- 提供图谱浏览、状态查看、导航和历史回放；
- 让工程师快速建立项目结构认知。

主要产物：

- 图谱视图；
- 节点详情；
- 关系解释；
- 搜索与过滤；
- 文档跳转；
- 变化时间线；
- 风险与待复查视图。

### 工作流 E：变化检测与 Git 集成

目标：

- 自动识别内容变化；
- 将 Git commit 与 KFlow 事件关联；
- 避免依赖人工执行 `modify`。

主要产物：

- 文件 fingerprint；
- Git diff 解析；
- `scan` / `status`；
- `impact --since <ref>`；
- commit / snapshot 关联；
- 可选的 pre-commit 或 Agent hook。

### 工作流 F：工程质量与迁移

目标：

- 保证重构过程中数据不丢失；
- 建立测试、版本和迁移机制。

主要产物：

- v0.1 数据迁移工具；
- schema version；
- 单元测试；
- 集成测试；
- 端到端场景测试；
- 崩溃恢复测试；
- 并发和锁策略；
- 发布流程。

### 工作流 G：Dogfooding 与验证

目标：

- 用真实项目验证 KFlow 是否减少 Token 和认知负担；
- 防止在抽象设计中失去真实场景。

建议测试项目：

1. KFlow 自身；
2. 一个文档依赖较复杂的软件项目；
3. 一次数学建模项目；
4. 后续可选 ONN 项目。

## 8. 分阶段路线图

## 阶段 0：冻结旧版本并建立重构基线

### 目标

保护当前成果，防止重构过程中失去参考。

### 任务

- 给当前主分支打版本标签；
- 确认当前测试可以稳定运行；
- 导出当前命令、数据格式和行为清单；
- 建立 `v2` 分支；
- 创建 `docs/product/`、`docs/architecture/`、`docs/adr/`；
- 建立重构 issue / milestone；
- 记录已知缺陷，但暂不修复非阻塞问题。

### 交付物

- `v0.1.0-legacy` 标签；
- 当前版本行为基线；
- v2 分支；
- 重构文档目录；
- 风险清单。

### 退出条件

- 旧版本随时可运行；
- 当前行为已有记录；
- v2 开发与旧版完全隔离。

## 阶段 1：产品发现与需求收敛

### 目标

把理念转化为可验证的真实工作流。

### 必须定义的核心场景

#### 场景 A：需求文档变化

```text
requirements.md 某章节更新
→ 系统识别变化
→ 发现 architecture 和 test-plan 受影响
→ Agent 只读取相关章节
→ Agent 更新文档
→ 人类确认
```

#### 场景 B：Agent 开始一个新任务

```text
用户要求修改某项设计
→ Agent 查询 KFlow
→ 获得目标、上游约束、直接下游和历史决策
→ 在限定上下文中完成任务
```

#### 场景 C：人类接管 AI 推进中的项目

```text
工程师打开图谱
→ 看见最近一周新增和修改的关键节点
→ 找到仍未人工确认的设计
→ 查看某项设计的来源和影响范围
```

#### 场景 D：方案被替代

```text
旧方案 A 被新方案 B 替代
→ 历史仍保留 A
→ 当前图谱默认展示 B
→ 依赖 A 的对象被提示迁移或复查
```

### 关键决策

- MVP 主要服务个人项目还是多人项目；
- 首个 Agent 集成目标是 Codex、Claude Code 还是通用 CLI；
- Node 首先支持文件级还是章节级；
- 图谱是本地 Web UI、桌面应用还是静态页面；
- 是否采用 event sourcing；
- 首版历史展示到什么粒度；
- 人工确认和 Agent 确认是否区别对待。

### 交付物

- 产品需求文档 PRD；
- 用户旅程；
- 用户故事与验收标准；
- MVP / P1 / P2 功能分层；
- 术语表；
- 非目标列表。

### 退出条件

- 每项 MVP 功能都能映射到至少一个核心场景；
- 不再使用“做一个更完整的知识图谱”之类不可验收描述；
- 已明确首个 Agent 和首个人类界面。

---

## 阶段 2：领域模型和架构原型

### 目标

在写大量业务代码前，验证 v2 的核心模型是否能表达真实场景。

### 任务

- 定义 KnowledgeObject；
- 定义 Relation 类型；
- 定义 ChangeEvent；
- 定义 ReviewRecord；
- 定义 ContextBundle；
- 定义状态计算规则；
- 定义 Git 元数据策略；
- 设计 schema version；
- 设计查询接口；
- 用 3 个真实项目样例手工建图；
- 验证是否能表达章节级、替代关系和历史事件。

### 强制原型

建立一个最小样例：

```text
requirement
→ constrained_by → architecture
→ implemented_by → module
→ validated_by → test
```

然后模拟：

1. requirement 内容变化；
2. architecture 需要复查；
3. module 受到传递影响；
4. test 需要重新执行；
5. architecture 被确认；
6. 旧 module 被新 module 替代；
7. 查询任意时间点的结构。

### 交付物

- 领域模型文档；
- JSON Schema 或等价契约；
- 架构图；
- 状态机；
- 事件模型；
- 关键 ADR；
- 手工样例数据。

### 退出条件

- 四个核心场景均能被模型完整表达；
- 不需要通过模糊字段或特殊分支补洞；
- 状态不再仅依赖红黄绿单字段；
- Git 历史与 KFlow 历史职责已明确。

---

## 阶段 3：核心引擎 v2

### 目标

实现不依赖 UI 的可靠知识与变更内核。

### 功能

- 对象和关系增删改查；
- schema version；
- Git 友好持久化；
- 自动索引重建；
- 文件与章节 fingerprint；
- 影响传播；
- 事件写入；
- ReviewRecord；
- 快照；
- 一致性检查；
- 错误恢复；
- v0.1 迁移。

### 工程要求

- 领域层不依赖 CLI 或 UI；
- 所有核心行为有单元测试；
- 写入过程具备事务或可恢复性；
- 索引是缓存，不是真相源；
- 事件不可静默覆盖；
- 对象和关系 ID 稳定；
- Git diff 可读；
- 并发写入有明确限制或锁。

### 交付物

- `kflow-core`；
- schema；
- migration；
- 单元测试；
- 集成测试；
- 示例项目；
- 开发文档。

### 退出条件

- 在无 UI 情况下可以完整完成核心场景；
- 人工破坏索引后可以恢复；
- 中途写入失败不会造成不可恢复状态；
- v0.1 示例可以迁移；
- 核心 API 稳定到足以支持 Agent 层。

## 阶段 4：Agent MVP

### 目标

证明 KFlow 能减少 Agent 的无效阅读和大规模文档纠错。

### 首批接口

建议至少支持：

```text
kflow status
kflow scan
kflow impact <target>
kflow impact --since <git-ref>
kflow context <target>
kflow context --task "<task description>"
kflow review-plan <target>
kflow confirm <target>
```

### ContextBundle 输出

必须明确：

- 目标对象；
- 必须读取的内容；
- 建议读取的内容；
- 只需摘要的内容；
- 受影响对象；
- 关系解释；
- 复查顺序；
- token 预算；
- 已排除对象及原因。

### 集成优先级

1. 通用 CLI + JSON；
2. Codex 可调用命令；
3. Claude Code Skill；
4. MCP Server；
5. 更深层 IDE / Agent 插件。

首版不应同时开发全部集成。

### 验证实验

对同一组文档更新任务比较：

#### 基线

- Agent 不使用 KFlow；
- 扫描整个文档群；
- 记录读取文件数、Token、时间和遗漏。

#### 实验组

- Agent 使用 KFlow ContextBundle；
- 只读取推荐上下文；
- 记录同样指标。

### 成功指标

建议初期目标：

- 无效文档读取量下降 50% 以上；
- Token 消耗下降 30% 以上；
- 关键影响遗漏率不高于基线；
- Agent 能解释为何读取每个文档；
- 更新后待复查范围可被人类理解；
- 端到端调用不要求用户手工维护大量命令。

### 交付物

- Agent CLI；
- JSON 契约；
- Codex 使用说明；
- 基准测试脚本；
- 评估报告；
- 示例提示词。

### 退出条件

- 至少一个真实项目证明 KFlow 能有效缩小上下文；
- ContextBundle 可稳定被 Agent 使用；
- KFlow 不是把“全量扫描”换成“全量预处理”；
- 影响范围错误可以被检测和修正。

## 阶段 5：Human Graph MVP

### 目标

让工程师快速理解结构、变化和风险，而不是只看一张漂亮图。

### 核心页面

#### 1. 项目总览

显示：

- 关键知识对象；
- 最近变化；
- 待复查对象；
- 未人工确认对象；
- 缺失来源；

#### 2. 图谱视图

支持：

- 节点类型过滤；
- 关系类型过滤；
- 状态过滤；
- 上下游展开；
- 影响子图；
- 时间范围；
- 点击打开文档；
- 聚焦当前任务。

#### 3. 节点详情

显示：

- 当前摘要；
- 文件或章节位置；
- 上游来源；
- 下游影响；
- 历史事件；
- 最近复查；
- 建立关系的证据；
- 人工 / Agent 贡献来源。

#### 4. 变化时间线

显示：

- 新增节点；
- 关系变化；
- 内容变化；
- 待复查产生；
- 复查完成；
- 方案替代；
- 快照。

### 技术建议

首版优先选择本地 Web UI：

- 易于跨平台；
- 可复用图可视化库；
- 便于从 CLI 启动；
- 可直接打开本地文件；
- 不需要立即开发桌面容器。

### 成功指标

- 新工程师可在 10 分钟内说清项目主要结构；
- 用户可在 30 秒内定位某项设计的来源；
- 用户可在 1 分钟内发现最近变化造成的风险；
- 图谱不是静态毛线团，而能围绕任务、影响和时间聚焦；
- 用户可以从图谱直接跳转到原始内容。

### 交付物

- 本地 Web UI；
- 图谱视图；
- 节点详情；
- 时间线；
- 文档跳转；
- UI 使用测试。

### 退出条件

- 图谱能回答实际问题，不只是展示节点；
- UI 和 Agent 使用同一 API；
- 人类看到的状态与核心引擎一致；
- 在中等规模项目中仍可用。

## 11. Codex 开发协作方案

### 11.1 不让 Codex 一次承担整个重构

应把工作拆成明确的、可验收的任务包。

每个 Codex 任务应包含：

- 背景；
- 当前架构；
- 本次目标；
- 非目标；
- 输入文件；
- 输出文件；
- 接口约束；
- 验收标准；
- 必须运行的测试；
- 禁止修改的范围；
- 完成后的自检清单。

### 11.2 建议的任务粒度

较好的任务：

- 定义并实现 `KnowledgeObject` schema；
- 为 `Relation` 增加 `impact_policy`；
- 实现文件 fingerprint 与变化检测；
- 实现影响子图查询；
- 实现 ContextBundle JSON；
- 为某个场景编写端到端测试。

不好的任务：

- “重构整个 KFlow”；
- “做一个知识图谱”；
- “把上下文管理做完整”；
- “优化架构和代码质量”。

### 11.3 每个阶段先写文档，再让 Codex 编码

推荐流程：

```text
产品说明
→ 领域模型
→ ADR
→ API 契约
→ 测试场景
→ Codex 实现
→ 自动测试
→ 人工评审
→ 合并
```

### 11.4 使用分支与小 PR

建议：

- 每个任务独立分支；
- 每个 PR 只解决一个明确问题；
- 不允许混入无关格式化和重命名；
- 先合并模型和契约，再合并实现；
- 大规模迁移必须单独 PR；
- PR 描述中写明受影响对象和风险。

### 11.5 要求 Codex 提供的完成报告

每次任务结束时必须输出：

- 修改了什么；
- 为什么这样设计；
- 哪些文件变化；
- 测试结果；
- 尚未解决的问题；
- 潜在兼容性风险；
- 是否偏离任务范围；
- 建议的下一步。

### 11.6 KFlow 应尽早用于开发 KFlow 自己

一旦最小 ContextBundle 可用，就应开始 dogfooding：

- 让 KFlow 管理自己的产品文档；
- 让 Codex 在修改架构时查询 KFlow；
- 记录真实 Token 和读取范围；
- 用自身缺陷推动功能设计。

## 13. 关键决策门

### 决策门 1：是否值得重构

通过条件：

- 已定义至少 3 个真实核心场景；
- 当前工具确实无法低成本满足；
- KFlow 的独特价值不是普通笔记图谱；
- 有明确评估指标。

否则：

- 暂停编码；
- 继续产品发现。

### 决策门 2：领域模型是否稳定

通过条件：

- 能表达文件、章节、设计决策和实验；
- 能表达变化、复查和替代；
- 能生成 Agent ContextBundle；
- 不依赖大量例外字段。

否则：

- 不进入核心引擎大规模实现。

### 决策门 3：Agent MVP 是否证明价值

通过条件：

- Token 或无效阅读显著下降；
- 影响遗漏不恶化；
- Agent 能稳定调用；
- 维护关系的成本可接受。

否则：

- 调整模型或产品方向；
- 不急于开发图形 UI。

### 决策门 4：人类图谱是否真的帮助理解

通过条件：

- 用户能快速回答结构、来源、影响和历史问题；
- 图谱不是不可读毛线团；
- 导航和过滤有效；
- 用户愿意持续打开它。

否则：

- 重新设计交互，而不是继续增加视觉效果。

### 决策门 5：是否进入长期产品化

通过条件：

- 至少两个真实项目持续使用；
- Agent 与人类两端均有明确收益；
- 数据模型稳定；
- 维护成本合理；
- 用户愿意将其加入日常工作流。

## 14. 主要风险与应对

### 风险 1：关系维护成本过高

问题：

- 用户和 Agent 不愿持续手工建立关系；
- 图谱很快过期。

应对：

- 只管理“重要知识对象”，不管理所有文件；
- 从显式高价值关系开始；
- 由 Agent 提议关系，人类抽查确认；
- 通过 Git diff 和文档结构自动辅助；
- 允许不完整图谱，但明确置信度。

### 风险 2：错误关系导致 Agent 漏读

问题：

- KFlow 过度缩小上下文，遗漏真实影响。

应对：

- ContextBundle 同时结合显式关系和保守检索；
- 区分强依赖与弱关联；
- 记录被排除对象及原因；
- 设置可调安全等级；
- 建立影响召回率测试。

### 风险 3：把全量扫描转移到后台

问题：

- KFlow 为生成关系或摘要，仍然频繁让 LLM 扫描全部文档。

应对：

- 核心依赖结构优先显式维护；
- 自动分析只处理变化增量；
- 摘要和 fingerprint 缓存；
- 所有后台 Token 都纳入成本指标；
- 不用“隐藏的全量扫描”伪装优化。

### 风险 4：图谱体验退化成毛线团

应对：

- 默认展示任务子图或影响子图；
- 支持按类型、状态、时间过滤；
- 聚合低价值节点；
- 强调导航、来源和风险，不追求全量展示；
- 为不同角色提供不同视图。

### 风险 5：历史模型过度设计

应对：

- 首版只记录高价值事件；
- 与 Git commit 建立关联；
- 先做时间线，再做完整时间旅行；
- 通过真实使用决定需要保存的粒度。

### 风险 6：Codex 产生大规模不可控修改

应对：

- 小任务、小分支、小 PR；
- 严格非目标；
- 每次要求测试和完成报告；
- 架构契约先行；
- 禁止在未批准情况下重写无关模块；
- 关键模型由人工评审。

### 风险 7：为了兼容 v0.1 妨碍 v2

应对：

- 旧版只作为迁移输入；
- 不保证所有旧行为原样保留；
- 优先保证数据可迁移；
- 必要时提供一次性迁移工具，而不是长期兼容层。

## 17. 项目经理建议

### 17.1 不要把“大规模重构”理解为“大规模编码”

真正的重构顺序应当是：

```text
重新定义问题
→ 收敛场景
→ 重构领域模型
→ 验证核心假设
→ 实现最小闭环
→ 用数据决定扩张
```

而不是：

```text
先重写全部代码
→ 再寻找产品价值
```

### 17.2 Agent 侧应先于人类 UI

原因：

- 当前痛点最明确；
- 成功指标更容易量化；
- 可以直接用于 KFlow 自身开发；
- 如果 Agent 上下文价值不成立，漂亮图谱不足以支撑项目；
- Human UI 可以复用已经稳定的核心 API。

### 17.3 历史功能应从事件开始，不从动画开始

先确保系统能可靠记录：

- 什么变了；
- 为什么变；
- 影响了谁；
- 谁复查了；
- 最终如何处理。

之后再考虑：

- 时间回放；
- 拓扑动画；
- 快照可视化；
- 方案演化图。

### 17.4 每个阶段都要有“停止条件”

KFlow 不应因为理念宏大而无限扩张。

每个阶段完成后都应问：

- 是否真的减少了 Agent 成本？
- 是否真的提升了人类理解？
- 关系维护成本是否可接受？
- 有没有更简单的方案？
- 下一阶段是否仍值得投入？

## 18. 最终推荐路线

推荐采用以下主线：

```text
冻结 v0.1
    ↓
产品与场景收敛
    ↓
领域模型与事件模型
    ↓
Agent ContextBundle 垂直切片
    ↓
真实项目基准测试
    ↓
核心引擎稳定化
    ↓
Human Graph MVP
    ↓
历史与审计增强
    ↓
多人协作与产品化
```

在数模国赛前，建议只推进到：

```text
产品定义
+
领域模型
+
Agent 垂直切片
+
一次真实验证
```

这足以判断 KFlow v2 是否走在正确方向，也能避免在赛前进入长期 UI 和基础设施工程。

---

## 19. 北极星原则

当后续出现功能争议时，优先选择更符合以下目标的方案：

> **让 Agent 少读、少猜、少做无效扫描；让人类看得懂结构、变化、风险和决策过程。**

任何功能若同时不能改善这两端中的至少一端，就不应进入当前优先级。
