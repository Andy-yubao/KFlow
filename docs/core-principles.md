# KFlow 核心原则

> 本文是 KFlow 产品与设计决策的最高层约束。具体领域规则见 [正式架构](architecture.md)，使用流程见 [KFlow 使用指南](kflow_skills.md)。

## 使命

KFlow 将原本散落在人类记忆、Agent 临时上下文和文档隐含语义中的项目知识结构显式化、持久化。

它帮助 Agent 缩小工作范围，也帮助人类持续理解和掌控项目。

## 北极星原则

> **让 Agent 少扫描无关文件，让人类始终掌握项目结构。**

KFlow 只维护重要文件、推导关系、影响状态和必要的拓扑历史。

它告诉 Agent 应该关注哪些文件以及为什么，但不替 Agent 读取、理解或修改文件；它让人类看懂项目当前结构和演化过程，但不试图取代 Git、编辑器或 Agent。

## 核心原则

### 1. KFlow 是项目结构的外部记忆

重要文件之间的关系、推导路径和影响范围，不应只存在于某次对话、某个 Agent 的上下文或某个人的记忆中。

KFlow 将这些结构保存为可持续维护、可被人类和 Agent 共同使用的项目事实。

### 2. KFlow 只指路，不代替 Agent 工作

KFlow 告诉 Agent：

- 哪些文件相关；
- 它们为什么相关；
- 哪些文件可能受到变化影响；
- 应优先检查哪些位置。

是否读取、如何理解、是否修改，仍由 Agent 根据当前任务和已有上下文自行决定。

KFlow 不传递文档正文，也不替 Agent 拼装上下文。

### 3. 显式关系优先于重复猜测

KFlow 的价值不在于让 AI 每次重新扫描全部文档并推测关系，而在于保存已经明确的重要知识拓扑。

AI 可以帮助建立和维护关系，但不能让“每次重新猜测”成为系统的核心工作方式。

### 4. 操作必须简单、原子、可组合

每个用户可见操作只完成一件明确的事，行为和副作用都应容易理解。

复杂工作流由 Agent 组合多个简单操作完成，而不是依赖大量高层、隐式、难预测的复合命令。

接口应尽可能容易被初次接触 KFlow 的 Agent 正确使用。

### 5. 人类和 Agent 使用同一事实

CLI、未来的 `kflow_skills.md`、图形界面和其他集成都必须建立在同一套项目事实之上。

人类看到的知识图谱，与 Agent 查询到的文件关系、影响状态和推导信息，不能来自两套不同逻辑。

### 6. KFlow 补充现有工具，而不取代它们

- Git 管理文件内容和版本历史；
- 编辑器负责阅读和修改；
- Agent 负责理解、判断和执行；
- KFlow 管理重要文件之间的拓扑、推导和影响范围。

当某项功能已经更适合由 Git、编辑器或 Agent 完成时，KFlow 不应重复实现。

## 决策过滤器

新增或修改任何功能前，先回答三个问题：

1. 它是否减少了 Agent 为判断影响范围而进行的无效扫描？
2. 它是否帮助人类更快理解项目结构、变化或风险？
3. 它是否侵入了本应由 Git、编辑器或 Agent 负责的工作？

若前两项都是否定的，该功能不应进入 KFlow。

若第三项是肯定的，通常也不应进入 KFlow。

## 关于 `kflow_skills.md`

核心原则文件回答：

- KFlow 为什么存在；
- KFlow 服务谁；
- KFlow 管理什么；
- KFlow 绝不做什么；
- 设计决策应依据什么。

`kflow_skills.md` 则回答：

- Agent 何时调用 KFlow；
- 每个操作如何使用；
- 返回结果如何解释；
- 修改前后应完成哪些步骤；
- 哪些行为必须避免。

理想的 `kflow_skills.md` 应当足够短。

如果需要大量例外和复杂说明才能让 Agent 正确使用 KFlow，优先怀疑 KFlow 的接口和操作设计，而不是继续扩充 Skill 文档。

## 文档分工

- 本文回答“为什么做、绝不做什么”；
- 领域模型回答“系统保存哪些事实、如何计算状态”；
- 使用场景回答“谁在什么情况下做什么、应得到什么结果”；
- `kflow_skills.md` 回答“Agent 如何正确调用这些能力”。

同一规则只在最合适的文档中完整定义，其他文档只引用，不复制长篇背景或历史讨论。
