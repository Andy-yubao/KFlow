---

## 1. 本文目的

本文只回答：

- 谁在什么情况下使用 KFlow；
- 用户或 Agent 能做什么；
- KFlow 应返回或展示什么；
- 哪些边界必须始终成立。

本文不固定：

- 最终命令名；
- CLI 参数；
- JSON 字段细节；
- fingerprint 公式；
- 存储布局；
- 事务实现；
- 内部类和模块结构。

具体实现必须服从本文，而不是反过来要求本文适配已有代码。

---

## 2. 文档结构

本文按四层组织：

### A. Agent 核心工作流

KFlow 最核心的价值闭环。
这是产品负责人需要重点审查的部分。

### B. 建图与维护能力

用于创建和维护 Node、Derivation 及其关系。
只关注用户可见行为，不展开实现细节。

### C. 系统验收要求

保证 KFlow 可靠、可解释、可恢复。
主要由设计和实现负责人负责。

### D. 后续规划

当前不阻塞核心版本，不应据此提前扩展范围。

# A. Agent 核心工作流

## A01 判断项目是否启用 KFlow

- 角色：Agent / 人类
- 场景：进入一个项目，准备处理重要文件。
- 动作：检查项目是否已经启用 KFlow。
- KFlow 返回：
  - 是否已初始化；
  - 当前 schema 是否可用；
  - 若不可用，说明原因。
- 边界：
  - 不自动初始化；
  - 不自动扫描所有文件建立图谱；
  - 不猜测哪些文件应纳入管理。

---

## A02 判断目标文件是否受 KFlow 管理

- 角色：Agent
- 场景：Agent 准备修改一个或多个文件。
- 动作：按文件路径查询其是否属于某个 Knowledge Node。
- KFlow 返回：
  - 是否受管；
  - 所属 Node 的稳定身份与名称；
  - 该 Node 的全部文件路径。
- 边界：
  - 未登记文件不是错误；
  - Agent 不需要预先知道 Node ID；
  - 普通项目文件不应被强制纳入 KFlow。

---

## A03 判断新文件是否值得纳入 KFlow

- 角色：Agent / 人类
- 场景：出现一个新的重要文件，或某个普通文件逐渐成为长期知识载体。
- 判断原则：

> **KFlow 不管理所有文件，只管理那些值得长期记住“它从哪里来、变化后影响哪里”的文件。**

一个文件通常适合纳入 KFlow，当它具备若干特征：

- 承载长期有效的项目知识；
- 会被人类或 Agent 反复使用；
- 与其他重要文件存在明确逻辑或推导关系；
- 它的变化可能要求检查其他文件；
- 遗忘其依据或影响范围会造成返工、冲突或无效扫描。

通常不应纳入：

- 临时草稿；
- 缓存、日志、构建产物；
- 自动生成且可重建的文件；
- 低价值中间输出；
- 大量普通源码文件；
- 只有主题相似、没有明确逻辑关系的材料。

- 边界：
  - Agent 不应为了图谱完整而静默登记所有文件；
  - 无法判断时，优先保持为普通文件，或向人类提出简短建议。

---

## A04 修改前查询上游前提

- 角色：Agent
- 场景：准备修改已管理的重要文件，但不确定其依据或约束。
- 动作：查询目标 Node 的 upstream 或直接 neighborhood。
- KFlow 返回：
  - 上游 Node；
  - 对应文件路径；
  - 经过的 Derivation；
  - 各输入在推导中的作用；
  - 稳定的拓扑顺序。
- Agent 决定：
  - 哪些文件已在当前上下文中；
  - 哪些需要重新读取；
  - 哪些只需知道其存在；
  - 是否已有足够信息开始修改。
- 边界：
  - KFlow 不返回正文；
  - KFlow 不自动打开文件；
  - 修改前查询不是所有任务的强制步骤；
  - 明显的拼写或格式修复可以跳过。

---

## A05 Agent 修改文件

- 角色：Agent / 人类
- 动作：使用编辑器或 Agent 自身工具修改真实文件。
- KFlow 行为：不参与正文编辑。
- 若修改的是派生 Node，Agent 应按需核对：
  - producing Derivation 的 inputs；
  - Derivation 的语义；
  - input/output 的作用描述；
  - sibling outputs 是否仍然合理。
- 边界：
  - 推导逻辑未变化时，不机械修改 Derivation；
  - KFlow 不创建、编辑、移动或删除用户正文。

---

## A06 扫描当前变化

- 角色：Agent / 人类 / 系统
- 场景：完成一轮文件或图谱修改后。
- 动作：执行只读扫描。
- KFlow 返回：
  - 哪些 Node 尚未确认；
  - 哪些 Node 自身文件变化；
  - 哪些 Node 的生产推导变化；
  - 哪些 Node 的直接输入条件变化；
  - 具体变化的文件路径；
  - 独立的 validation issues。
- 边界：
  - 不依赖人工声明“我修改了文件”；
  - 不自动确认；
  - 不修改用户正文；
  - 不把校验错误伪装成普通 review 状态。

---

## A07 查询影响范围与检查顺序

- 角色：Agent / 人类
- 场景：扫描发现变化后，需要确定处理范围。
- 动作：查询本次变化的影响。
- KFlow 返回：
  - changed Nodes；
  - affected Nodes；
  - 每个 Node 的全部文件路径；
  - 直接影响和传递影响；
  - 影响深度；
  - 来源变化根；
  - 经过的 Derivation；
  - 可解释影响路径；
  - 当前 reasons 与 issues；
  - 稳定的 `review_order`。
- 语义：

> 这些位置可能需要检查。

而不是：

> 这些文件一定错误，必须修改。

- `review_order` 规则：
  - 上游先于其受影响下游；
  - 同层顺序稳定；
  - 只是一种建议检查顺序，不自动执行。

---

## A08 按顺序检查受影响 Node

- 角色：Agent
- 动作：按 `review_order` 逐个检查 Node。
- 对每个 Node，Agent作出三种结论之一：

### A. 需要修改

- 读取文件；
- 完成必要修改；
- 重新扫描；
- 根据新结果继续处理。

### B. 不需要修改

- 确认上游变化没有破坏该 Node；
- 不修改正文；
- 单独确认该 Node。

### C. 暂时无法判断

- 保留 `needs_review`；
- 不为了清空列表而强行确认。

---

## A09 单独确认一个 Node

- 角色：Agent / 人类
- 场景：某个 Node 已经完成检查。
- 动作：对该 Node 执行确认。
- 含义：

> 该 Node 已经在当前文件、当前生产推导和当前直接输入条件下完成检查。

- KFlow 返回：
  - 确认前的变化原因；
  - 确认后的当前状态；
  - 仍待处理的下游摘要。
- 边界：
  - 一次只确认一个 Node；
  - 不级联；
  - 不自动确认 sibling outputs；
  - 不自动确认下游；
  - 确认不代表 KFlow 证明文档绝对正确；
  - 存在阻断性 validation issue 时拒绝确认。

---

## A10 查看剩余待处理范围

- 角色：Agent
- 场景：完成一次或多次确认后。
- 动作：查看本次维护闭环还剩下什么。
- KFlow 返回：
  - 仍为 `needs_review` 的相关 Node；
  - 剩余 `review_order`；
  - 仍存在的 validation issues；
  - 与本次变化根有关的未完成范围。
- 边界：
  - 不要求整个项目所有 Node 都变为 current；
  - 只要求闭合本次变化产生的影响范围。

---

## A11 本次维护闭环完成

一次任务在以下条件满足时结束：

- 本次计划修改的文件已经处理；
- 项目已重新扫描；
- 本次变化根产生的影响范围已经检查；
- 需要修改的 Node 已完成修改；
- 不需要修改的 Node 已单独确认；
- 不存在阻断本次流程的 validation issue；
- 本次影响范围内不再有未处理的 `needs_review` Node。

项目中可以保留与本次任务无关的历史未确认 Node。

---

## A12 两种合法工作方式

### 先规划，再集中修改

适用于影响范围较小、拓扑清楚的任务。

```text
查询上游
→ 查看预期影响
→ 读取必要文件
→ 集中修改
→ 扫描
→ 逐 Node 确认
```

### 逐层推进

适用于影响范围较大、修改过程中可能发现新问题的任务。

```text
修改一个 Node
→ 扫描
→ 处理直接下游
→ 确认
→ 继续下一层
```

KFlow 不强制唯一工作流。

# B. 建图与维护能力

## B01 初始化 KFlow 项目

- 建立规范元数据结构；
- 建立缓存与运行时忽略规则；
- 重复初始化明确报错。
- 不自动读取正文建图；
- 不自动创建用户文件。

---

## B02 创建 Node

- 将一个或多个已存在文件登记为一个 Knowledge Node；
- 返回稳定 ID、唯一名称和全部文件路径；
- 新 Node 可以暂时孤立；
- 没有生产者时视为源 Node。

必须校验：

- 文件存在；
- 路径规范；
- 文件未归属于其他 Node；
- Node 名称唯一。

---

## B03 修改 Node

允许：

- 修改显示名；
- 增加绑定文件；
- 移除绑定文件。

规则：

- 稳定 ID 不变；
- 文件集合变化会使目标及其下游需要检查；
- KFlow 不替用户移动或重命名真实文件。

---

## B04 删除 Node

- 只删除 KFlow 元数据；
- 不删除真实文件；
- 不能留下悬挂 Derivation 引用或非法图；
- 若暂时不能安全删除，应拒绝并返回关联关系。

具体护栏由领域模型和实现共同完成，不要求 Agent 学习复杂删除模式。

---

## B05 创建 Derivation

- 连接已有 input Node 与 output Node；
- 支持多输入、多输出；
- input 和 output 均至少一个；
- output 当前没有其他生产者；
- 图必须保持无环；
- Derivation 不拆成普通二元边；
- 不引入固定关系类型枚举。

---

## B06 修改 Derivation

允许修改：

- 整体 short/detail；
- input/output short/detail；
- input 集合；
- output 集合。

规则：

- 修改后必须保持图不变量；
- 任何语义或拓扑变化都会使其 outputs 及下游可能需要检查；
- producer 变化通过修改相关 Derivation 表达；
- 不要求 Agent 学习独立 `rewire` 概念。

底层如需同时修改多个对象，必须由事务保证一致性。

---

## B07 删除 Derivation

- 只删除 Derivation 元数据；
- 不删除 Node；
- 不删除用户文件；
- 必须明确报告：
  - 哪些 output Node 因此失去生产者；
  - 哪些下游可能受到影响；
  - 哪些确认基线因此不再适用。

旧 Confirmation 保留为版本检查基线；失去生产者的 output Node 显示 `derivation_changed`，下游按直接输入版本变化显示 `input_changed`。

---

## B08 查询单个 Node 或 Derivation

支持按以下方式定位：

- 稳定 ID；
- Node 名称；
- 文件路径。

返回其规范元数据、直接关系和状态摘要。

---

# C. 系统验收要求

本节是实现必须满足的工程契约，不要求产品负责人逐条决定内部实现。

## C01 图与元数据完整性

系统必须检测：

- 重复 ID；
- 重复 Node 名称；
- 重复文件归属；
- 缺失文件；
- 悬挂引用；
- 多生产者；
- input/output 重复或交叉；
- 零 input 或零 output Derivation；
- 环；
- schema 损坏；
- Confirmation 结构损坏、目标 Node 不存在或编码与 schema 不兼容。

无生产者 Node 与孤立 Node 均合法。

Confirmation 记录的文件、生产者或输入基线与当前事实不同，是可解释的 review reason，不是 validation issue。

---

## C02 Confirmation 的基本语义

Confirmation 是某个 Node 最近一次完成检查时的版本基线。

它不是：

- 审批；
- 绝对正确证明；
- 永久绿色状态；
- Git commit；
- 简单布尔值。

系统必须能根据当前事实与该基线比较，解释：

- 文件是否变化；
- 生产推导是否变化；
- 直接输入条件是否变化。

---

## C03 稳定、可解释的状态

状态由当前事实计算，不持久化简单颜色。

至少应区分：

- `unconfirmed`
- `files_changed`
- `derivation_changed`
- `input_changed`
- validation issues

同一 Node 可以同时具有多个 review reason。

---

## C04 确定性输出

- 相同事实产生相同结果；
- 排序稳定；
- review order 稳定；
- 机器输出带 schema version；
- 成功结果与错误分离；
- 错误类型明确。

---

## C05 原子写入与一致性

- 单对象写入不能留下半写文件；
- 多对象更新失败后不能留下不可恢复的不一致状态；
- 简单用户操作与可靠内部事务必须同时成立。

---

## C06 缓存可重建

删除缓存和索引后，应能从规范元数据和当前文件重建：

- Node 与 Derivation 图；
- 生产者与消费者索引；
- 当前状态；
- 影响范围；
- review order。

---

## C07 Git-native

进入 Git：

- ProjectManifest；
- Node；
- Derivation；
- Confirmation。

不进入 Git：

- cache；
- lock；
- runtime 临时文件；
- 可重建索引。

切换到历史 commit 后，应能重建该版本的拓扑和确认基线。

---

## C08 零正文泄漏

任何 Agent 接口都不得返回：

- 文档正文；
- 文件片段；
- 自动摘要；
- 拼装 Prompt；
- 从正文提取的临时上下文包。

只返回：

- 文件路径；
- Node；
- Derivation；
- 显式语义；
- 状态；
- 影响范围；
- 校验问题。

---

## C09 单工作区可靠性

首个版本只需保证单工作区、单写者可靠使用。

暂不承诺：

- 多写者自动合并；
- 分布式锁；
- 实时协作冲突解决。

---

# D. 后续规划

以下能力不阻塞核心版本，必须在核心闭环稳定后单独立项。

## D01 人类项目总览

展示：

- 关键 Node；
- 最近变化；
- 待复查；
- validation issues；
- 高影响节点。

---

## D02 人类图谱导航

支持：

- 上下游展开；
- 影响子图聚焦；
- 任务相关过滤；
- 避免默认展示不可读全量图。

---

## D03 Node 与 Derivation 详情界面

展示：

- 文件路径；
- 生产推导；
- 消费推导；
- sibling outputs；
- 当前状态原因；
- 最近确认情况。

---

## D04 Git 拓扑历史比较

按稳定 ID 比较两个 Git 版本中的：

- Node 新增、删除、修改；
- Derivation 新增、删除、修改；
- 拓扑结构变化。

不实现事件重放或时间旅行数据库。

---

## D05 v1 一次性迁移

仅在核心领域模型稳定后实现：

- 只读预检；
- 必要人工补全；
- 输出独立 v2 数据；
- validate 与对账；
- 显式切换；
- 不原地覆盖 v1；
- 不修改正文。

---

## D06 MCP、Web UI 与深度 Agent 集成

分别立项，不与核心领域模型绑定。

---

## D07 候选知识文件辅助发现

未来可以帮助 Agent提出候选 Node 建议，但：

- 不静默登记；
- 不根据主题相似性直接创建 Derivation；
- 不替代显式关系维护。

---

# 3. 当前不提供的能力

明确排除：

- 章节、段落、代码片段级 Node；
- 固定关系类型枚举；
- `supersedes` / `replaces` 特殊关系；
- 正文 ContextBundle；
- 自动摘要和 Prompt 拼装；
- 持久化红黄绿状态；
- 人工 `modify` 标记；
- 级联确认；
- 自动改写下游文件；
- 自动关系猜测；
- 自动登记全部文件；
- event sourcing；
- 快照数据库；
- 时间旅行引擎；
- 身份审批系统；
- 首版多写者并发合并。

---

# 4. 首个垂直切片

第一轮实现只验证以下闭环：

```text
判断项目是否启用
→ 按文件定位 Node
→ 查询 upstream / neighborhood
→ Agent 修改文件
→ scan
→ 查询影响范围与 review_order
→ 逐 Node 检查
→ 单独 confirm
→ 查看剩余影响
```

第一轮暂不实现：

- 完整建图 CLI；
- 完整删除策略；
- v1 迁移器；
- 人类图谱；
- Git 历史比较；
- MCP；
- Web UI；
- watcher；
- 自动候选文件发现。

---
